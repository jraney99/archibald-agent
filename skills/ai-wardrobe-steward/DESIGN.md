# AI Wardrobe Steward — Design Spec (v3)

Status: living design document. v3 is a philosophy-level rewrite, not a feature addition — v1/v2 were still shaped like an app wearing a conversational skin (upload flows, questionnaires, mandatory calibration steps). This version removes that shape entirely. Nothing here should ever read like a wizard, a form, or an onboarding sequence, because none of those things exist in this product.

## Why this exists

Started as "an AI that recommends outfits like a stylist would." That's shallow on its own — it only answers "what should I buy." The real product is a **relationship**: an agent that quietly gets better at knowing someone the way a trusted human stylist does, over months and years of ordinary conversation, not through a setup process.

**The test for every design decision in this document: would a great human personal stylist behave this way?** A good stylist doesn't hand you a 30-question intake form before agreeing to help. They don't make you upload your entire closet before they'll talk to you. They notice things over time — what you bought, what you wore twice and loved, what you tried once and never touched again — and they get sharper with every conversation, not because you filled out a profile, but because you talked to them. If a feature wouldn't survive that comparison, redesign it.

Core philosophy:

- **The agent onboards itself. The user never onboards.** There is no setup phase, no required first session, no percentage-complete profile bar. Understanding accumulates from ordinary use — "I bought this jacket," "I like how JFK dressed," "these pants didn't fit" — each one a lesson, none of them a form field.
- **Stewardship over consumption.** The AI is not a salesperson. It helps users buy less, buy better, use what they own, and maintain what they own.
- **Timeless over trendy.** Prioritize quality, fit, materials, longevity, personal identity over fast fashion and trend-chasing.
- **The wardrobe should become more valuable over time** — fewer pieces, each more meaningful, better fit, longer life.
- **People can't articulate taste, but they can react to it.** Prefer "I like this / I don't like this" over abstract questionnaires. Photos and reactions teach the agent faster than descriptions do — but they're one input among many (purchases, wear history, fit feedback, offhand comments), never a required upload gate.
- **The agent may infer. It may never assume.** Everything it extracts from a photo, a receipt, a comment, or a pattern in behavior is a hypothesis until the user confirms it. Confirmed hypotheses become memory; unconfirmed ones stay hypotheses, visibly.
- **Silence is correct behavior, not a missing feature.** An agent that speaks up only when it has something genuinely useful to say is doing its job. An agent that checks in constantly is failing at it, no differently than a stylist who calls you every day would be insufferable rather than attentive.

**Non-goals:** This is not a financial tracker (purchase price is stored for cost-per-wear math, not as a second ledger competing with a user's actual finance tools), not a trend/fast-fashion engine, and not a sales funnel — the default lean on any purchase question is toward "skip / already own something similar," not a neutral 3-way recommendation. It is also not an app with screens — there is no "closet screen," "shopping screen," or "style profile page" anywhere in this design, conceptually or literally. There is only conversation, and what the agent chooses to do in response to it.

## Architecture: engine vs. profile

Built as a reusable template, so the skill logic and any one person's data must be cleanly separable:

- **Engine** (shipped, reusable, no personal data): controlled vocabularies, care heuristics, outfit-matching logic, module instructions, prompt templates.
- **Profile** (private, per-installation, fully swappable): one user's style identity, measurements, closet inventory, wear/outfit history, feedback history — each preference carrying its own confidence score (see Confidence-Scored Memory below), because a profile built from ordinary conversation is never uniformly certain the way a filled-out form would be.

A fresh install should work with an empty profile and no code changes. Nothing in the engine may hardcode a specific user's brands, sizes, or preferences.

**External integrations are optional hooks, not hard dependencies.** Weather, calendar/travel dates, and reminder/notification delivery are useful but must degrade gracefully if the host environment doesn't have them wired up — the skill should ask the user directly ("what's the weather/occasion?") rather than fail when an integration isn't present. This is what makes it portable across different users' setups.

## Conversation is the interface

There is no menu of modules to choose from, and the user should never need to know the module boundaries exist. "Should I buy this?" might touch the closet, the style profile, the body/fit profile, and the purchase-decision log in one exchange — the agent decides which parts of its own memory are relevant to a given message, the same way a stylist doesn't announce "now entering shopping-advice mode" before answering a question. The module breakdown below is how the *engine* is organized internally (for the sake of building and maintaining it coherently) — it is never a structure the user is asked to navigate, confirm, or step through.

## Passive learning and deep calibration

Two ways the agent's understanding grows — one is the default, the other is offered, never required.

**Passive learning (the default, and for most users the only mode that ever runs).** The user simply talks. Every message is a potential lesson: a purchase mentioned in passing, a brand name dropped, a complaint about fit, a photo shared because it was convenient to share, feedback on how something felt to wear. The agent extracts what it can from ordinary conversation and asks nothing extra. No session, no setup, no required first conversation — this works identically whether it's message one or message one thousand.

**Deep calibration (optional, occasional, never required).** If the agent's confidence in a preference is low and that gap is actually limiting what it can do well, it may *offer* — not require — a calibration moment: reviewing the style profile so far, sending 5-10 photos of outfits the user loves, entering measurements, reviewing brand history. Always phrased as an offer with an easy no ("Want to spend a minute improving my recommendations? Totally optional — happy to keep going as-is otherwise"), never as a gate blocking some other capability, and never repeated on a schedule — track when it was last offered and let a real, long gap or a clearly relevant moment (not a timer) justify asking again. Declining costs the user nothing.

**A closet photo catalog is the same pattern, aimed at the inventory instead of the profile.** This is deliberately *not* a new onboarding flow — it's the identical shape as deep calibration above (an offer, tracked so it's never repeated, costs nothing to decline), just triggered by a thin closet instead of thin confidence. It stays inside the anti-patterns rule below precisely because it's an offer: it never blocks anything else from working (a closet with zero items still answers questions, generically), it's suggested once and tracked via its own `closet_catalog_last_offered` field (kept separate from `calibration_last_offered` since they're offers about different things), and it's never re-suggested once the closet has real depth or the offer's already been made. What makes v1/v2's photo-upload gate an anti-pattern was that it was *required* and *repeated* — an occasional, declinable offer was never the part that failed the "would a stylist do this" test; a stylist saying "bring a few pieces so I get a feel for things" passes it fine.

## Confidence-scored memory

Every learned preference carries three independent numbers, not just a binary "confirmed or not": **confidence** (how certain), **importance** (how much it should weigh), and an **evidence trail** (what actually built it). This is what lets the agent behave the way a stylist actually does — increasingly sure about some things, still guessing about others, weighing a core trait more than a trivial one even at equal certainty, and able to say *why* it believes something instead of asserting a plausible-sounding guess.

**Confidence** — how certain the agent is this is true:
- **Stated directly** ("I hate skinny jeans") starts at high confidence (90+).
- **Inferred from a pattern** (three navy purchases in a row, no one ever commented on) starts lower (50-70) and is never presented as settled fact until it either gets confirmed directly or accumulates enough consistent signal.
- **Inferred from a single indirect signal** (one photo, one offhand comment) starts lower still (30-50) — a hypothesis, not a memory yet.
- **Rises with repetition and direct confirmation**, not with time passing on its own.

**Importance** — how much a preference should weigh in a recommendation, independent of how certain it is. A trivial-but-certain fact (always wears black socks) shouldn't carry the same weight as a core trait (prefers classic over trendy) even at equal confidence — and a preference stated with real emphasis ("I refuse to wear logos") should start at high importance immediately, on message one, regardless of how many times it's been reconfirmed. Confidence and importance can diverge from the very first mention; they are not the same axis measured twice.

**Evidence** — a short, dated, capped trail of what actually built the confidence (the specific mentions, purchases, or reactions), not just the current number. This is what makes "why do you think that?" answerable honestly — citing something real — rather than an invitation to fabricate a plausible-sounding explanation after the fact. Without it, an explanation feature would be a hallucination risk dressed up as a relationship feature.

**Low confidence is what triggers a natural clarifying question**, folded into normal conversation at a moment it's actually relevant — never a standalone "let me ask you some questions" interruption. If it's never relevant, it's fine for a low-confidence entry to just sit there indefinitely; nothing forces resolution.

**Fit preferences additionally support per-context overrides** — a preference can differ by occasion (relaxed casually, structured for business-formal), keyed by the same occasion-tier vocabulary the Outfit Engine already filters on rather than inventing a parallel concept. A context override is a full preference in its own right (its own confidence, importance, evidence), not just an alternate value.

This replaces treating "uncertain" as a boolean flag to clear before something counts as real — uncertainty is a spectrum the agent should be honest about at every point on it, not a state to escape as fast as possible. And a single number was never enough to also capture "how much does this matter" or "why do I believe this" — those needed their own explicit representation rather than being silently folded into confidence.

**Noticing drift is a byproduct of dated evidence, not a separate tracking system** — a preference whose evidence is mostly old, next to a different preference gaining fresh evidence, is a real drift signal computable from data already being kept. Surfacing it is still bound by the same rule as everything else here: on-demand or contextually relevant, phrased as an observation ("I've noticed...") never a verdict, and never pushed proactively on a schedule — that would be the exact notification-shaped failure mode this whole design exists to avoid.

## Universal rules (apply to every module below)

1. **The agent may infer. It may never assume.** Anything extracted from a photo, receipt, comment, or behavioral pattern is a hypothesis with a confidence score until the user confirms it — at which point, and only then, it becomes memory. ("I believe this is a Barbour Ashby waxed jacket from the pocket layout, but I couldn't see the interior label — is that right?") No module silently mutates the profile, closet, or history based on an inference alone.
2. **Uncertainty is a first-class output, not a gap to paper over.** Low-confidence reads are surfaced as "here's my read, correct me," never asserted as fact. Quality and durability judgments should be grounded in observable construction cues (stitching, material, hardware, silhouette) the AI can actually see, not static brand-reputation priors, which go stale and quietly undermine the trust the whole relationship depends on.
3. **Controlled vocabularies over free text** (defined below) — occasion, formality, season, item state, condition. Outfit matching and analytics can't work reliably against inconsistent free text. This applies to structured, comparable fields; it does not mean flattening taste itself into categories a stylist wouldn't recognize (see Style Identity below).
4. **Derive, don't store, anything computable.** "Compatible items" for a given piece is computed by the outfit engine at request time from color/formality/season rules — never stored as a static field that goes stale the moment the closet changes.
5. **Silence is correct behavior.** Speak up when there's something genuinely useful to say — a watchlist match, an item due for care, an answer to a direct question. Do not speak up on a schedule for its own sake. A week where the agent found nothing worth mentioning is a week where it did its job correctly, not a week it has to justify.

## Anti-patterns (things this skill deliberately does not do)

Named explicitly because "application thinking" tends to creep back in through small, individually-reasonable-looking additions:

- No onboarding flow, wizard, setup session, or "let's get started" moment of any kind.
- No mandatory upload of any kind — not 30 photos, not the whole wardrobe, not measurements. Ever.
- No questionnaires. Preferences come from reactions and conversation, not forms.
- No progress bars, completion percentages, or "profile 60% complete" framing — a profile is never incomplete, it's just as far along as it's been talked about.
- No daily check-ins, and no notification "just to stay engaged." Every unprompted message must earn its interruption.
- No random or unsolicited shopping suggestions outside a confirmed watchlist entry.
- No re-asking a question the user already answered because a differently-named module happens to store it — one memory, referenced everywhere it's relevant.

## Controlled vocabularies

- **Occasion tier:** casual / smart-casual / business-casual / business-formal / black-tie / athletic / loungewear (extensible, but outfit/closet logic matches against this fixed list, not free text)
- **Formality scale:** 1 (loungewear) → 5 (black-tie), numeric so it can be compared/ranged
- **Season:** spring / summer / fall / winter / all-season
- **Item lifecycle state:** `active` / `dirty` / `at-cleaner-or-repair` / `packed-away` / `lent-out` / `retired`. The outfit engine only recommends `active` items — this is what closes the "recommends a shirt that's actually at the dry cleaner" gap.
- **Condition rating:** excellent / good / worn / needs-repair

These vocabularies exist for the closet's structured fields (things that need to be compared, filtered, and matched by the outfit engine) — they are never used to flatten how style preferences themselves get expressed or stored (see Style Identity).

## Modules

The engine's internal organization — never exposed to the user as separate destinations, screens, or steps.

### 1. Style Identity
No image-first *calibration step* — the days of "upload 10-30 reference images before continuing" are over. Photos, screenshots, comments, and reactions are all just conversation, arriving whenever they arrive, weighted by confidence rather than gated behind a required batch. When visual references would genuinely sharpen a fuzzy read, the agent may suggest it, framed as an offer with real value attached, not a checklist item: "I think I have a decent read on your style, but a few outfits you actually love would sharpen it — if you've got 5-10 handy." Produces a versioned, confidence-scored profile; a new signal is diffed against the current profile and confirmed before it overwrites anything, never silently.

**Style Identity / Genome layer.** Individual preferences (a color, a material, a brand) are one thing; a coherent identity synthesized across many of them is another — "likes navy" vs. "classic American, coastal, rugged, refined." A human stylist forms this kind of synthesis naturally, without ever asking a client to fill out an archetype quiz, so this layer is built the same way: `archetype` (a single short phrase, low confidence off one or two signals, rising only with repetition), `pillars` (several coexisting threads, e.g. "Ivy League refinement" + "rugged heritage," each independently confidence/importance-scored), `desired_impression` (how they want to come across), and `anti_identity` (what they're consciously moving away from — often surfaces as a rejection, not a proactive statement). Same `{value, confidence, importance, evidence}` shape as every other preference, stored in `profile/style_identity.yaml`, one layer of synthesis above `style_profile.yaml`. It emerges from connecting things already said, never from a direct "what's your archetype?" question — the question this layer answers is one the agent asks of its own accumulated data, not one it puts to the user.

### 2. Body & Fit Profile
Measurements + fit preferences + per-brand sizing learned over time ("Medium in Brand A, Large in Brand B") — each carrying its own confidence. No measurement is ever required to use the rest of the skill; fit-critical recommendations just stay appropriately hedged until the relevant number exists. Explicit unit field (imperial/metric) captured the first time it's actually needed, not upfront. Confidence in a measurement should be revisited (not blindly trusted) if it's been a long time (e.g. >12 months) before leaning on it for something fit-critical.

### 3. Digital Closet
The inventory. Schema per item includes the controlled-vocabulary fields above (lifecycle state, condition, formality, season) plus photos, category, brand, material, purchase price/date, wear count. "Compatible items" is explicitly NOT a stored field (see universal rule 4). Grows one mention at a time ("I finally replaced my belt") exactly as naturally as it grows from a deliberate afternoon of batch-cataloging — both are first-class, neither is the "correct" way to do it.

**Foundation garments are inventory, not styling input.** The `basics` category group (socks, underwear, undershirts, sleepwear) is tracked for replacement, laundry, and spend, but is absent from `outfit_slots` and skipped by duplicate/redundancy analytics — a stylist doesn't compose around a sock drawer, and owning fifteen identical pairs is a stocked drawer, not a purchase mistake. Care & Maintenance and closet-value reporting still count them.

**A tracked `wear_count` of 0 is ambiguous for a pre-existing item** — it can't distinguish "genuinely never worn" from "worn constantly for years before this skill existed to track it." `estimated_frequency` (`regularly`/`occasionally`/`rarely`/`basically-never`) closes that gap: a one-time, self-reported baseline captured at intake for an already-owned item (most relevantly during a batch photo-catalog pass), never inferred, never revised automatically. Wardrobe Analytics reads it to keep "never worn" from being asserted about something the user already said they wear regularly.

**Retiring an item shouldn't be a dead end.** `disposition` (`donated`/`sold`/`given-away`/`discarded`), plus an optional `disposition_value` and `disposition_date`, record what actually happened once `lifecycle_state` becomes `retired` — only meaningful in that state, never set otherwise. This is what lets closet_value reporting show recouped value, not just money spent, which is the second half of the stewardship story ("buy less, buy better" is a stronger claim when it can also show "and got something back for what didn't work out").

### 4. Intake (photo / receipt / manual / conversational mention)
One module, not several, because every path feeds the same closet record and needs the same safeguards:
- Every intake path runs through **de-dup matching** (brand + category + color + purchase-date proximity) before creating a new item — otherwise the same blazer entered via photo and receipt becomes two records.
- Every AI-extracted field (brand from a logo, material from a photo) carries a confidence score and is confirmed before writing, per universal rule 1.
- Receipt/purchase data is captured for cost-per-wear analytics only — it is not a competing financial ledger.

### 5. Outfit Engine
Generates outfits from `active`-state items given occasion/weather/calendar inputs (via optional hooks, or asked directly). **Tie-break rule** for the repeat-avoidance vs. favorites conflict: a favorite (top-rated, high-repeat-satisfaction) outfit is exempt from the "avoid recent repeats" cooldown — repetition of a favorite is a feature, repetition of a random combination is not.

**Color harmony is a compositional tiebreaker, never a filter.** Real candidates are already fixed by the deterministic filtering step; `color_families` (neutral/warm/cool) is reference data the agent uses to break ties between multiple valid combinations — a neutral base plus at most one non-neutral accent generally reads better than two competing saturated colors. This is advisory judgment support, not a controlled vocabulary — an item's `color` field stays free text, matching universal rule 3's distinction between structured fields and taste itself.

### 6. Shopping Advisor & Personal Shopper
Merged — evaluating a specific item a user found and searching for an item to fill a need are the same judgment engine with two entry points. Runs every candidate through: need vs. want, closet duplication, construction-quality read (not brand priors), cost-per-wear projection. Per the stewardship principle, ties default to "skip" or "you already own something close," not a neutral buy/consider/skip split.

**Extended with a watchlist for "keep looking," not just "answer this one request."** Entries come from a direct ask or a confirmed closet gap (never auto-added from a gap without asking — a reported gap isn't automatically a want). A scan reads the active watchlist, searches for real candidates per entry, and runs any hits through the exact same evaluation above — the watchlist is a different way of feeding the judgment engine, not a second judgment path. Silence when nothing worthwhile turns up is correct behavior, not a gap. The skill has no background process of its own; "constantly looking" requires an external recurring trigger (optional hook, same pattern as weather/calendar) to actually start a scan.

**Recommendation reasoning is a required four-factor check, not a prompt-driven afterthought:** identity fit (does it match the Style Identity archetype/pillars, or the anti-identity list), wardrobe fit (does it complement or duplicate what's active — pulling from closet-overlap and Wardrobe Analytics' redundancy/gap data), functional need (a real recurring gap vs. a want dressed up as one), and longevity (would this still make sense in years, weighed against trend-dependence). A recommendation should be traceable to at least one of these, never bare enthusiasm ("this looks cool"). An emotional motivation ("everyone's wearing it") is acknowledged plainly, not corrected or moralized about — it still goes through the same four-factor read, and the read (not judgment about the motivation) is what informs the verdict.

**Purchase Lessons — regret memory.** A purchase that turns out to be a mistake ("I never wear these pants," "this brand always runs weird on me") is a lesson the same way any other feedback is, categorized (`fit`/`brand`/`color`/`quality`/`lifestyle`/`other`), confidence-scored, evidence-backed, and consulted on future similar recommendations — the concrete mechanism behind "a good stylist remembers what didn't work," not just a promise. Stored in `profile/purchase_lessons.json`, same confirm-before-write discipline as everything else that becomes memory; a new lesson matching an existing one reinforces rather than duplicates.

### 7. Wardrobe Analytics
Reports tied explicitly back to the skill's stated success metrics (fewer unnecessary purchases, higher usage rate, more intentional buying) rather than raw stats in a vacuum — a report that doesn't answer "are we winning against these goals" isn't done.

**The closet is a system with roles to fill, not a flat list.** Beyond usage and pairwise duplicates: redundancy clusters (3+ active items in the same category/color serving the same purpose — a stronger signal than a single pairwise duplicate flag) and role coverage (occasion tiers with no active item actually tagged for them, as a complement to the formality-derived coverage-gap read, since tagging is optional and the two views disagreeing is itself informative). All computed from existing closet fields — no new required data, and gaps are reported structurally ("no active footwear in this formality range"), never as a fabricated specific recommendation ("buy a brown loafer") the underlying data can't actually support.

**Money in is only half the picture** — `closet_value` also reports what's actually been recouped from retired items (via `disposition_value`) and a net-invested figure alongside the raw total, so a closet that resells or donates well is a measurable, reportable outcome rather than something only asserted in prose.

### 8. Care & Maintenance
Needs a real default heuristics table, not just "consider wear frequency and material" as a principle — e.g. wool suit → dry clean every ~5 wears, leather shoes → condition every ~15 wears or after weather exposure, watch → service interval by movement type. Defaults are overridable per item as the user gives feedback ("that jacket needs cleaning less often than you'd think").

**Two different questions, two different views.** "What's due for care" (an interval-based heuristic against wear count/elapsed time) and "what's sitting in the hamper right now" (a flat aggregate of everything currently `dirty`, grouped by category) look similar but answer different prompts — the first is about a cleaning schedule, the second is about whether today is worth a laundry run. Kept as separate read-only views rather than merged into one, since conflating them would make neither answer cleanly.

**Seasonal transitions are a natural moment to revisit `packed-away`, not a scheduled nag.** When a season change actually comes up in conversation, a read-only lookup of packed-away items tagged for the incoming season turns "it's getting cold" into a specific, real offer ("your wool coat and that scarf are still packed away — want them back in rotation?") instead of either silence or an unprompted check-in. Same "optional hook, ask directly otherwise" treatment as weather/calendar elsewhere in this skill — no external trigger required, but one could drive it if the host environment has one.

### 9. Travel Packing
Capsule wardrobe + packing list from destination/duration/activities. Should accept these via an optional calendar/travel-itinerary hook rather than always asking the user to re-type dates that exist elsewhere in their environment — but must work from direct user input if no such hook exists.

### 10. Continuous Learning / Feedback Loop
Single loop, not two separate modules layered on outfit generation. Feedback ("did this fit well," "would you buy it again") is **sampled, not asked after every outfit** — asking after everything produces survey fatigue, which is exactly the "application thinking" this whole redesign exists to remove. Trigger feedback prompts on: new items' first wear, low-confidence outfit suggestions, and explicit user ratings — not every single day. This is also where confidence scores across the whole profile get revised — a compliment, a returned item, a "wore it twice and never again" pattern all move a confidence number, the same way a stylist's sense of a client sharpens through the relationship rather than through review sessions.

**Stylist self-reflection.** A relationship this long-running needs the agent to be able to answer, honestly, "what do I currently believe about this person?" — high-confidence beliefs, still-uncertain ones, and possible contradictions (a liked and an avoided entry that overlap in a way worth reconciling). This is computed entirely from data already kept (`style_profile.yaml`, `style_identity.yaml`, `body_fit_profile.yaml`) — nothing new is stored, matching universal rule 4 (derive, don't store, anything computable). Like style-evolution noticing, it's answered on demand or when directly relevant, never volunteered on a schedule; a self-assessment nobody asked for is still an unprompted check-in, no better than any other one this design rules out.

### 11. Colour Analysis

A professional seasonal colour analysis (the kind a colour consultant produces — a named season, a palette of specific swatches, an undertone, colours to avoid) is a different kind of input from everything else in this skill: it's **expert-stated fact, not passively-accumulated taste**. It doesn't start as a low-confidence hypothesis and climb — it arrives authoritative, from someone paid to be right about it, and should carry real weight from message one. So it does *not* use the `{value, confidence, importance, evidence}` shape; it's structured reference data in `profile/color_analysis.yaml` with a `source`, an `analysis_date`, and a versioned `change_log` — closer in spirit to `body_fit_profile.yaml`'s `units` than to a style preference.

**The palette is hex-coded, and matching is deterministic.** The whole point of a professional analysis is precision the user can't eyeball — "is this specific teal one of mine, or is it a touch too warm?" is exactly the question they paid to have answered. So `scripts/color_match.py` converts the palette to CIELAB and scores a candidate colour by CIEDE2000 (perceptual distance), returning `in-palette` / `borderline` / `reject`. It rejects a colour that lands closer to an explicit out-of-palette swatch than to anything in the palette, and it rejects warm/golden undertones even when a raw hex distance looks close — because "reads warm" is the actual rule a Soft/Cool season lives by, and hex distance alone doesn't capture it. Leather goods get their own allowed-browns list and skip the warm reject (a tan suede shoe is fine where a tan shirt isn't). The **model** still decides what colour a garment actually is, from a photo or a listing, and passes a hex; the **script** only scores it. This is the same division of labour as the Outfit Engine (deterministic filtering, model composition).

**It's an input to other modules, not a destination.** Nobody asks to "open colour analysis." It feeds: the Shopping Advisor (a dedicated colour-fit step — off-palette, especially warm, is a firm objection, never an absolute veto: the guide itself says "a guide, not a rulebook"), the Outfit Engine (prefer priority families, compose low-contrast for a Soft season, keep leather harmonised), Wardrobe Analytics (what fraction of the active closet is actually in-palette — surfaced only on request, never as an unprompted "your things are wrong" message), and eyewear/fabric/metal guidance that rides along with the same consultation. Closet items store an optional `palette_match` snapshot computed at intake, so analytics doesn't have to re-derive it.

**A fresh install has no colour analysis, and everything still works** — `color_match.py` exits cleanly with "nothing to match against," the Outfit Engine falls back to the generic warm/cool/neutral `color_families` tiebreaker, and the Shopping Advisor simply skips the colour-fit step. The analysis is a capability that switches on when the data exists, not a dependency.

## Success metrics (unchanged, now the thing Analytics reports against)
Fewer unnecessary purchases, faster outfit creation, better closet understanding, increased usage rate, more intentional purchases, longer clothing lifespan, higher confidence.

## Decisions

**Profile data format — split by purpose.** YAML for style identity, measurements, and settings (human-curated, occasionally hand-edited, matches this workspace's finance skill conventions). JSON for closet inventory and wear/outfit history (growing structured records, appended/read programmatically, matches this workspace's CRM/finance transaction logs).

**Every stored preference is `{value, confidence, importance, evidence}`, not a bare value.** This is the concrete form of confidence-scored memory above — style categories, colors, materials, brands, avoidances, fit preferences, measurements, and the Style Identity layer (archetype, pillars, desired impression, anti-identity) are all stored this way (fit preferences additionally carry optional per-occasion `contexts`). A confidence-free value would silently regress to the "confirmed or not" binary this redesign specifically replaces; a confidence-only value would still be unable to distinguish a certain-but-trivial fact from a certain-and-central one, or answer "why do you believe that" with anything but a guess. Purchase Lessons deliberately use a lighter version of the same shape (`confidence` + `evidence`, no `importance`) — a lesson's weight comes from what kind of mistake it categorizes as, not a separate importance axis; adding one here would be complexity without value (PART 7's rule, applied to the schema itself).

**Photo storage/retention.**
- `profile/photos/closet/<item-id>.jpg` — one canonical photo per closet item, kept indefinitely. This is the inventory; it's never disposable.
- `profile/photos/inspiration/` — style reference images, arriving whenever they arrive, never as a required batch. Attributes (colors, silhouettes, formality) get extracted into the style profile; the raw image itself is optional to retain once distilled, not load-bearing.

**Onboarding shape — there is no onboarding shape.** The agent's first interaction with a brand-new profile looks exactly like its thousandth interaction with a well-established one: it uses whatever it currently knows (possibly nothing) and does its best with the request in front of it, filling gaps through the conversation itself rather than deflecting into a setup flow. "I don't have anything in your closet yet — want to tell me about a few pieces, or should I just answer generically for now?" is a fine thing to say once, in the moment it's actually needed; it is never a gate the user has to clear before anything else works.

**Testing framework — resolved: scripted eval scenarios over synthetic data, not unit tests over internal functions.** `tests/run_eval.py` runs every script against valid and adversarial synthetic profile data, asserting on exit codes and output, then restores the real `profile/` directory. This matches how the skill's real bugs actually got found during development — by running scripts against edge cases, not by reading code — so that's what stays automated rather than a traditional unit-test suite over internal functions (there isn't much internal function-level logic here; almost everything is instructions to a model plus scripts that read/write files).

**Two layers within `run_eval.py` itself: per-script tests and workflow tests.** Most tests exercise one script in isolation against hand-built synthetic data — this catches a script's own edge cases but can't catch a bug in how two scripts' outputs actually feed each other in sequence. A dedicated "end-to-end workflow" section chains real script invocations in the order an actual conversation would produce them (draft a closet item → confirm it → the Outfit Engine finds it → wearing it logs history and bumps wear_count → Wardrobe Analytics reflects it, and equivalent full lifecycles for Style Identity, Body & Fit, Shopping Advisor, the watchlist, Purchase Lessons, Care & Maintenance, Travel Packing, and Colour Analysis — including a colour that reads in-palette by raw distance but is caught by the warm-undertone reject) — this is what actually verifies the workflow logic holds together as a system, not just that each piece works alone.

**A second, deliberately different testing artifact exists alongside it: `tests/relationship_scenarios.md`.** `run_eval.py` can verify a script's behavior against synthetic data, but it has no way to grade whether an actual conversation *felt* like a good stylist — that's a model-judgment question, not a deterministic assertion. The scenarios file is a documented checklist (New User, Closet Addition, Shopping Decision, Six-Month Relationship, and others) meant to be run by a human or another agent periodically, graded against the "would a great human personal stylist behave this way" test — not something `run_eval.py` executes, and not pretended to be.

**Three more testing tools, each catching a failure mode the others structurally can't:**
- **`tests/audit_vocab_coverage.py`** — a static, code-level audit, not a behavioral test. It imports the confirm/validate script pairs directly and cross-checks their real constants against each other and against `vocab.yaml`, plus a source-text lint that every write-path CLI argument pulling from a controlled vocabulary (occasion, season, formality, category, lesson type...) actually references the matching vocab key somewhere in its own file. This exists because the real bug pattern found repeatedly during stress-testing wasn't a script misbehaving against bad data — it was a field wired into *some* but not *all* of vocab.yaml/confirm-script/validator (`fit_preferences.bottoms.length` and `outfit_history.py log --occasion` were both exactly this), which only ever surfaced by manually testing that one specific field. This makes the whole class of gap show up automatically.
- **`tests/mutation_check.py`** — checks whether the test suite itself is doing real work. Each mutation reverts one specific fix made during development (a removed bool-guard, a loosened tolerance, a missing existence check) in an isolated temp copy of the skill, then confirms the test suite actually fails against it. A mutation that survives (every test still passes) is a real blind spot, not a false alarm — this is how the "rejected the diff, but only because a *separate* post-write validator caught it after the write already happened" gap was found: several tests asserted the confirm scripts' exit code without checking that the write itself never happened, so a mutated pre-write check could still exit nonzero for the wrong reason and the test wouldn't notice.
- **`tests/fuzz_test.py`** — property-based testing, stdlib `random` only (no third-party dependency, matching this skill's stdlib+PyYAML constraint on the scripts themselves). Instead of hand-picked adversarial examples, it generates randomized diffs (mixed-type confidence/importance, empty/whitespace/unicode/very-long strings, malformed evidence, invalid context keys) across hundreds of iterations per script, checking invariants rather than specific expected outputs: never crash, never partially write on a rejected diff, never accept something the corresponding validator would then reject. Fixed seed for reproducibility.
