## Files

- `vocab.yaml` — controlled vocabularies (engine, reusable, no personal data): categories, occasion tiers, formality scale, seasons, lifecycle states, condition ratings. Every closet item's enum fields must come from here — never invent a new value inline. The `basics` category group (`socks`, `underwear`, `undershirt`, `sleepwear`) is foundation-garment inventory only — see "Basics" under How items enter the closet.
- `profile/closet.json` — the actual inventory. One JSON array of item records. This is personal data (this installation's) — swappable per user.
- `profile/photos/closet/<item-id>.jpg` — one canonical photo per item, copied from the source file the user shared (see "How items enter the closet" below for exactly when/how).
- `profile/photos/inspiration/` — visual references, arriving whenever they arrive, same copy mechanism, used by Style Identity.
- `scripts/check_photos.py` — audits `closet.json`'s `photo` fields against what's actually on disk: broken references (field set, file missing), active items with no photo yet, and orphaned files nothing references.
- `scripts/show_photos.py` — prints ready-to-send `MEDIA:<path>` lines for one or more item ids (or `--search "<term>"`), for relaying verbatim on any "show me a photo of X" query — see Queries below for why this replaced hand-typed `MEDIA:` lines.
- `scripts/closet_dedup.py` — checks a candidate item against existing items for likely duplicates.
- `scripts/validate_closet.py` — validates `closet.json` against `vocab.yaml` after any write.
- `scripts/closet_bulk_state.py` — sets `lifecycle_state` across every item matching a category/season/id-list/current-state filter in one call (dry run by default, `--apply` to commit). For "pack away all my X" style requests, see Lifecycle state discipline below. Also the mechanism for a single item — there's no separate one-item path.
- `profile/pending_closet_additions.json` — drafted items awaiting confirmation (see "How items enter the closet" below).
- `scripts/confirm_closet_item.py` — `--list` shows the pending queue; `<id>` or `--all` moves item(s) into `closet.json` and validates.
- `scripts/cancel_closet_item.py` — `<id>` or `--all` drops pending item(s) without ever writing to `closet.json`.
- `profile/style_profile.yaml` — style categories, preferred colors/materials/brands, fit notes, persona, avoidances, inspirations — every entry `{value, confidence, importance, evidence}` — plus `calibration_last_offered` and `closet_catalog_last_offered` (plain date-or-null bookkeeping, not confidence-scored preferences, so a deep-calibration or photo-cataloging offer never gets repeated on a schedule) and a `change_log` (it's versioned, per DESIGN.md — updates never silently overwrite it). Both `_last_offered` fields are set via `confirm_style_update.py`'s `set` like anything else, just with a plain date string instead of a `{value, confidence, importance}` object.
- `profile/pending_style_update.json` — a single proposed diff to the style profile awaiting confirmation (not a queue — one change under review at a time).
- `scripts/confirm_style_update.py` — `--show` prints the pending diff; no argument applies it (bumps `version`, stamps `last_updated`, appends to `change_log`, then auto-runs `validate_style_profile.py`). `add` on a value that already exists (case-insensitive) merges into it — confidence/importance replaced, evidence appended and capped at 5 — instead of duplicating. `remove` matches by plain value, not a full object.
- `scripts/validate_style_profile.py` — independent structural check on `style_profile.yaml`, including that every entry is a proper `{value, confidence, importance}` object (both scores 0-100) with well-formed `evidence` if present. Since this file is deliberately YAML for hand-editability, this is the safety net for edits made outside the confirm script entirely — run it any time, not just after a scripted write.
- `scripts/cancel_style_update.py` — discards the pending diff without touching `style_profile.yaml`.
- `profile/style_identity.yaml` — the Style Identity / Genome layer: `archetype` (scalar), `pillars`/`desired_impression`/`anti_identity` (lists) — same `{value, confidence, importance, evidence}` shape, one level of synthesis above `style_profile.yaml`'s individual preferences.
- `profile/pending_style_identity_update.json` — a single proposed diff awaiting confirmation, same pattern as the style profile.
- `scripts/confirm_style_identity_update.py` / `scripts/cancel_style_identity_update.py` / `scripts/validate_style_identity.py` — same mechanics as the style-profile trio above, applied to `style_identity.yaml`.
- `profile/color_analysis.yaml` — a professional seasonal colour analysis (e.g. a Soft Summer analysis from a colour consultant). Season/undertone/intensity/contrast, the full palette (~70 swatches by family, each `{hex, name, family}`), a separate `leather_palette`, `exclude` rules + `hard_reject` swatches, `metals`, `fabric_finish`, `combination_styles`, `footwear`, `eyewear`. **Not** the `{value, confidence, importance, evidence}` shape — this is expert-stated reference data with a `source` and a versioned `change_log`, closer in spirit to `body_fit_profile.yaml`'s `units`. See "Colour Analysis" below.
- `profile/pending_color_analysis_update.json` — a single proposed diff awaiting confirmation, same pattern as the style profile. `{"review_summary": "...", "set": {<field>: <value>}}` — a `set` replaces a whole top-level field (the initial import sets everything; a later tweak sets just what changed).
- `scripts/confirm_color_analysis_update.py` / `scripts/cancel_color_analysis_update.py` / `scripts/validate_color_analysis.py` — same trio pattern; `validate_color_analysis.py` checks `season`/`undertone`/`contrast_level` against `vocab.yaml`, well-formed hexes, `family` values against `palette_families`, and that `core_colors` name real palette swatches.
- `scripts/color_match.py` — **the deterministic colour tool.** `--hex "#4C98A2"` matches a candidate colour against the palette using CIEDE2000 (perceptual distance) and returns `{verdict: in-palette | borderline | reject, nearest_palette, warm_undertone_flag, reason}`. Rejects a colour that lands closer to a `hard_reject` swatch than to anything in-palette, and rejects warm/golden undertones even when a hex looks close (unless `--context leather`, which checks the leather list and allows warmer browns). Also `--name "teal"` (fuzzy palette lookup), `--list-family blue-greens`, `--families`. The model decides what colour a garment *is* and passes the hex; this script only scores it.
- `profile/body_fit_profile.yaml` — measurements, fit preferences (tops/outerwear/bottoms rise-leg-length-break), and `brand_sizing` history ("Medium in Brand A, Large in Brand B") — measurements and fit preferences are `{value, confidence, importance, evidence}`; fit preferences can additionally carry per-occasion `contexts` overrides. `units` and `measurements.measured_date` are plain values (a unit system and a timestamp aren't taste preferences with uncertainty attached). Same versioned-diff pattern as the style profile.
- `profile/pending_body_fit_update.json` — a single proposed diff awaiting confirmation.
- `scripts/confirm_body_fit_update.py` — `--show` prints the pending diff; no argument applies it, then auto-runs `validate_body_fit_profile.py`. `set` keys are dot-paths (e.g. `measurements.chest`, `fit_preferences.bottoms.rise`) so nested fields can be updated individually; a `set` merges into whatever's already there — value/confidence/importance replaced when given, evidence appended and capped, and a `contexts` update merges context-by-context rather than replacing the whole dict, so correcting one occasion's override never discards the default or the others. `add` on `brand_sizing` matches an existing (brand, category) pair and merges into it the same way. Rejects (without writing) any fit-preference value not in `vocab.yaml`'s `fit_preference_scales`, any `units` value not in `unit_systems`, a measurement whose `value` isn't numeric, a context key that isn't one of `vocab.yaml`'s `occasion_tiers`, or any entry missing a valid `confidence`/`importance`.
- `scripts/cancel_body_fit_update.py` — discards the pending diff without touching `body_fit_profile.yaml`.
- `scripts/validate_body_fit_profile.py` — independent structural check on `body_fit_profile.yaml` (measurement/fit-preference `{value, confidence, importance, evidence}` shape including nested `contexts`, `units`, `brand_sizing`/`change_log` shape). Same rationale as the style profile validator.
- `scripts/brand_sizing_lookup.py` — fuzzy-matches a brand against `body_fit_profile.yaml`'s `brand_sizing` (optionally narrowed by category), reporting each match's confidence and most recent evidence. The factual grounding for Shopping Advisor's fit-critical sizing step, below.
- `scripts/outfit_candidates.py` — given an occasion (and optional season), returns the real `active` closet items that fit, grouped by outfit slot (base_top/layering_top/bottoms/outerwear/footwear/etc.). Deterministic filtering only — never invents an item.
- `scripts/calendar_outfit_candidates.py` — reads all connected calendars through the shared wrapper, normalizes explicit attire/event phrases, and returns only new or changed upcoming events that warrant proposals.
- `profile/outfit_proposals.json` / `scripts/outfit_proposals.py` — event-version deduplication, planned-versus-worn state, selected item IDs, assumptions, weather context, and post-event confirmation.
- `scripts/send_outfit_proposal.py` — sends the verified JPEG board with event-scoped Telegram buttons.
- `profile/style_signals.json` / `scripts/style_learning.py` — low-confidence behavioral proposal feedback kept distinct from durable preferences until repetition or explicit confirmation supports a profile update.
- `profile/outfit_history.json` — log of outfits actually worn: date, occasion, item ids, `favorite` flag. Powers repeat-avoidance and the favorite tie-break.
- `scripts/outfit_history.py` — `recent --days N` lists recent outfits (repeat check); `log --occasion ... --items id1,id2,...` records a worn outfit, bumps each item's `wear_count`/`last_worn`, and flags any first wear (one of the three Continuous Learning feedback triggers); `favorite <id>` / `unfavorite <id>` marks an outfit as a keeper, exempting it from repeat-avoidance; `feedback <id> --note "..." [--favorite | --unfavorite]` records a reaction and optionally toggles favorite in the same call.
- `scripts/shopping_closet_check.py` — given a category (and optional formality/season), returns every closet item in that category regardless of lifecycle state, with realized cost-per-wear where computable. The factual grounding for both Shopping Advisor entry points below.
- `profile/purchase_decisions.json` — every Shopping Advisor recommendation given, and later what the user actually did about it. The only way "fewer unnecessary purchases"/"more intentional buying" (DESIGN.md success metrics) become measurable rather than asserted.
- `scripts/purchase_decisions.py` — `log --category ... --recommendation <buy|skip|already-own> --reasoning "..."` records a recommendation as soon as it's given; `outcome <decision-id> --action <bought|skipped> [--linked-item <id>]` records what actually happened; `report [--days N]` breaks down recommendations/outcomes and flags overrides (advised skip/already-own, bought anyway) — the number that actually matters for the stewardship metric.
- `profile/purchase_lessons.json` — regret memory: mistakes noticed after the fact ("I never wear these pants"), turned into `{lesson_type, item_description, linked_closet_item_id, lesson, confidence, evidence}` records future recommendations actually consult, not just prose the agent has to recall.
- `profile/pending_purchase_lessons.json` — a queue of drafted lessons awaiting confirmation (each needs its own `id` assigned when drafted, e.g. `lesson-slim-chinos`).
- `scripts/confirm_purchase_lesson.py` — `--list` shows the queue; `<id>` or `--all` confirms. A new lesson matching an existing one (same `lesson_type` + a similar `item_description`) reinforces it — confidence/lesson text updated, evidence appended and capped at 5 — instead of duplicating.
- `scripts/cancel_purchase_lesson.py` — `<id>` or `--all` discards without writing.
- `scripts/validate_purchase_lessons.py` — structural check against `vocab.yaml`'s `purchase_lesson_types` and `closet.json` (if `linked_closet_item_id` is set, it must actually exist).
- `scripts/purchase_lessons_lookup.py` — fuzzy-matches a category/keyword against recorded lessons, optionally narrowed by `lesson_type`. The factual grounding for Shopping Advisor's lesson-check step.
- `scripts/style_reflection.py` — read-only aggregation across `style_profile.yaml`/`style_identity.yaml`/`body_fit_profile.yaml`: high-confidence beliefs, uncertain ones, possible contradictions (literal text overlap between a liked and an avoided entry), and entries not reconfirmed in 180+ days. Grounds "what do you believe about me?" answers.
- `profile/shopping_watchlist.json` — things to keep looking for: user-requested ("let me know if a good navy overcoat under $400 shows up") or gap-detected (a confirmed `closet_report.py` gap). The data the proactive scan flow reads from.
- `scripts/shopping_watchlist.py` — `add --category <cat> [--max-price N] [--formality N] [--season <s>] [--brands "A,B"] [--notes "..."] [--source user-requested|gap-detected]` creates an entry; `list [--status active|fulfilled|cancelled|all]` (defaults to `active`); `fulfill <id> [--linked-item <closet-id>]` and `cancel <id>` close one out; `touch <id>` stamps `last_checked` after a scan pass.
- `profile/product_history.json` / `scripts/product_history.py` — stable retailer/product/variant identity with bounded price and stock snapshots, prior verdict, and change detection so scans do not repeatedly surface unchanged products.
- `scripts/data_quality.py` — reports missing photos, sizes, palette assessments, prices, unclosed shopping outcomes, and the number of confirmed wears. Unknown facts stay unknown until supplied.
- `scripts/init_profile.py` — creates an empty private profile for a fresh installation without mixing personal data into the reusable engine.
- `profile/comfort_profile.yaml` / `scripts/comfort_profile.py` / `scripts/calibration.py` — progressive, one-question-at-a-time thermal comfort evidence and predictions using feels-like temperature, wind, rain, activity and outdoor duration.
- `scripts/outfit_score.py` — ranks complete active-item combinations deterministically for occasion, palette, recent repetition, condition and layering context before model judgment.
- `scripts/calendar_outfit_watch.py` / `scripts/post_event_watch.py` — no-model polling and post-event confirmation; model work occurs only when a real proposal is needed.
- `scripts/calendar_travel_watch.py` — no-model travel detector that wakes the capsule-packing workflow only for new calendar travel.
- `profile/purchase_lifecycle.json` / `scripts/purchase_lifecycle.py` — orders, shipments, delivery, return deadlines, fit verdicts and kept/returned outcomes.
- `profile/source_health.json` / `scripts/source_health.py` — retailer source availability kept separate from product stock state.
- `profile/activity_overrides.json` / `scripts/activity_policy.py` — per-item preferred, allowed, excluded and exclusive activities, layered over conservative category/catalog defaults.
- `profile/laundry.json` / `scripts/laundry_day.py` — his laundry days and the skipped-week safety net; the silent daily cron that returns washed clothes to `active`.
- `profile/activity_preferences.json` / `scripts/activity_policy.py prefer|venue` — how the wearer personally dresses for an activity (occasion tier + slot categories) and which named venues mean which activity; overrides the generic `vocab.yaml` mapping.
- `scripts/travel_packing.py` — given a comma-separated list of occasions the trip needs (and optional season), returns the combined real `active` candidate pool across all of them, deduped by item and annotated with which occasion(s) each one covers — the data a capsule wardrobe gets built from.
- `scripts/seasonal_review.py --season <season>` — lists `packed-away` items tagged for the given season (or `all-season`), so an actual season change ("it's getting cold") can prompt a specific "want to bring these back into rotation?" instead of a vague reminder. Read-only, deterministic filtering only — it never flips `lifecycle_state` itself; that's a `closet_bulk_state.py` call once the user confirms which items are actually coming back. No calendar hook is wired up, so this is triggered by the season actually coming up in conversation, not on a timer.
- `scripts/closet_value.py` — total money invested in the closet (sum of `purchase_price`), broken down by category and lifecycle state. A real sum from real data — items missing a price are excluded and called out, never assumed to be $0. Also reports what's actually been recouped from retired items via `disposition_value` (sold/etc.), a net-invested figure (total minus recouped), and a breakdown by `disposition` type — money in is only half the stewardship picture.
- `scripts/closet_report.py` — usage (most worn; zero-wear items split into genuinely **never worn** vs. **no tracked wears yet, but self-reported usage on file** via `estimated_frequency` — see "Capturing a self-reported usage baseline" below), possible duplicates (same category, similar color, close formality — among `active` items), redundancy clusters (3+ serving the same purpose), coverage gaps (which occasion tiers have no complete outfit available), and role coverage (counts by `occasion_tags`). All computed from existing closet fields, no new data required.
- `references/holderness-bourne.md` — an example per-brand reference (Holderness & Bourne, a `preferred_brands` entry): the fabric decision axis, the fit model and the style list with list prices. Read it whenever the Shopping Advisor is evaluating an item from that brand. Colourways rotate and aren't listed — run each candidate through `color_match.py`.
- `references/wardrobe-plan.md` — the user's deliberate finished-wardrobe plan: the target set (with per-category counts, gaps, and cull targets), a **wear-capacity ceiling per category (§2a)** — the hard limit on how much of a category can actually be worn in a year — a 3-phase build sequence, a budget frame, cost-per-wear reference numbers, and a **spending-posture section that changes the Shopping Advisor's default posture for the user** (permission-first for gaps *under* the ceiling, for a user who tends to under-buy; but the wear-capacity ceiling overrides that and is a firm limit). Read whenever evaluating a purchase, a cull, or a "should I buy" for the user.
- `care_heuristics.yaml` — default care intervals by category and material (engine, reusable): wear-based (e.g. wool blazer → dry clean every ~5 wears) except watches, which are time-based (mechanical movements degrade from disuse, not wear) — and a quartz watch's battery-change cadence is different again from a mechanical/automatic's actual service interval, if `movement_type` is set on the item. Each entry also carries a `drying` instruction, separate from the cleaning `action` — how something dries is a different failure mode than how it's cleaned (a wool sweater survives hand-washing and then gets ruined by a hot dryer).
- `scripts/care.py` — `check` lists everything due for care right now, including its drying instruction where one exists; `laundry` is a different, simpler question — an aggregate of what's marked `dirty` right now grouped by category ("is it worth doing a wash today"), not an interval-based due-list; `log --item <id> --action "..."` records maintenance performed (resets that item's wear-since-care counter); `override --item <id> [--interval-wears N | --interval-days N] [--action "..."] [--drying "..."]` layers a correction on top of the default for one item — only the fields given are replaced, the rest is still inherited from the category/material default.
