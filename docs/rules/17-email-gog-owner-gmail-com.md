## Email (gog · owner@example.com)
**Default channel for people:** When asked to check if someone responded, replied, or messaged — search email first via `gog`. Do not ask whether to check email or Telegram. Almost all of the user's meetings and correspondence come through email. Only check Telegram if the user explicitly says so or the context is clearly a Telegram thread.

**Email search fallback — run this exact sequence before asking the user anything:**
1. `gog gmail messages search --account owner@example.com "from:[sender first name]" --max 5 -j`
2. `gog gmail messages search --account owner@example.com "subject:[keyword]" --max 5 -j`
3. `gog gmail messages search --account owner@example.com "from:[name] [keyword]" --max 5 -j`
4. `gog gmail messages search --account owner@example.com "newer_than:3d" --max 20 -j`
Once a message ID is found, read the body with `python3 ~/.openclaw/workspace/Skills/shared/read_email_body.py MESSAGE_ID` — HTML-stripped and quote-trimmed, unlike raw `gog gmail get` (which has no plain-text format; only `full|metadata|raw` exist — there is no `--format text`). If a booking/itinerary email's details (flight number, times, confirmation) aren't legible after this, that means the email itself doesn't contain them — do not ask the user to supply details a proper read should have surfaced; only ask if the clean-text read genuinely lacks them.
Note: `gog gmail search` returns thread IDs; `gog gmail messages search` returns message IDs. Always use `messages search` when you need to read body content. Only after all 4 attempts fail: ask the user for clarification. Never ask the user to supply sender, subject, or search terms — that is what searching is for. If the sender name, subject, or message ID is already visible anywhere in the current session, use it immediately without searching.

Prefer drafts over sending. Signoff: `Best,` / blank line / `The user`. Resolve recipient: Contacts → Gmail history → ask the user. Show To/Cc/Bcc in every draft. All writes (send, reply, forward, delete, label, archive, move): Confirmation Protocol. Never forward without explicit approval. Never store email content in memory. Verify with `gog` output before claiming completion.

**Updating an existing Gmail draft:** Before making any change, state what is currently in the draft, show exactly what will change, then Confirmation Protocol → ✅ → update → verify by draft ID.

**Email monitor daemon commands:** The `com.openclaw.email-agent` daemon monitors Gmail and sends notifications to Telegram. OpenClaw handles all user responses — the daemon does NOT poll Telegram itself.
- **Relevance threshold:** Surface mail only when it directly affects the user: security/access concerns, required actions, substantive personal messages, or material updates about his own accounts, investments, bookings, health, home, purchases, and active services. A relationship with the sender alone is insufficient. Surveys, feedback requests, generic education, product announcements, cross-sells, engagement nudges, and promotions are clutter even when they come from a company the user uses; route recurring examples toward exact-address unsubscribe/Trash proposals.
- `/pending` or `pending` → read `gmail_pending` from `~/.openclaw/email_monitor_state.json`; list each entry as: `N. To: [to_email] | Re: [subject]\n[first 80 chars of draft]…`. Empty → "No pending drafts."
- `/cancel` → remove the most recent `gmail_pending` entry (and matching `tg_pending` entries sharing that `gmail_msg_id`) from the state file; confirm: "❌ Cancelled draft to [to_email]."
- Email sending requires a current, exact proposal approval: `send_pending.py --approval-id <id>`. Create/reissue buttons with `shared/show_pending_proposal.py email --id <gmail_msg_id>` after drafting; the owner-scoped dispatcher validates the approval and current draft. Never use raw gog send/reply/autoreply or infer approval from recency.
- **Free-text reply to an email notification = a DRAFT REVISION, never a send.** Any message that says what to reply, how to respond, the outcome to relay, or a wording/tone change — `"tell them X"`, `"let them know Y"`, `"reply that Z"`, `"say I approved it / it's cleared / to try again"`, `"make it warmer"`, a grammar fix — is an instruction to *rewrite the pending draft*, not to send anything and not to compose a new email yourself. Steps: (1) pick the entry — the `gmail_msg_id` from the notification's `ref:` line if present, else the single / most-recent `gmail_pending` entry; (2) rewrite `gmail_pending[<id>]["draft"]` (and the `draft` field of any `tg_pending` entries sharing that `gmail_msg_id`) to incorporate the instruction, one signoff only (`Thanks,` / `Best,` + `The user`), no doubled signature; (3) show the **full** revised draft in a standalone block; (4) end with `✅ to send`. Do NOT send until a literal ✅ then `send_pending.py <id>`.
- **"Sent" is a claim you earn from output, never from intent.** Do not say sent / done / "told them" / "let them know" for an email until `send_pending.py` ran *this turn* and its stdout starts with `SENT:`. A failed or un-run send that you narrate as success is a false report (Critical Operating Rules), not a rough edge.

**Inline button callbacks (daemon proposals):** See `Documentation/rules/05-inline-button-callbacks-confirm-skip.md` for the full `confirm:*` / `skip:*` dispatch table.

**Relevance policy lives in one module:** `Skills/email-monitor/scripts/email_policy.py` classifies every subject as security / material / marketing / unknown and holds the rule-evidence thresholds, the Trash action + security guard, and the registry of dedicated catch-up paths (telehealth appointment reminders, OpenTable, Travel label, and the finance watcher crons). The daemon, the one-tap proposals, the audit and the migration planner all import it — change policy there, never in a copy.

**Recurring-sender auto-filing (fully automatic):** Before proposing a blanket filter, the daemon samples up to 30 messages from the exact address over 90 days (Trash included, Spam excluded, display-name matches discarded) and classifies them with `email_policy`. It only proposes label-and-archive when at least two samples are consistently records (material). It only proposes Trash/unsubscribe when at least two are consistently marketing. Any security sample, any mixture, any unclassified subject, or fewer than two samples keeps the sender under message-level triage. Proposals show the history counts used for the decision. Known sender domains and destination labels live in `Skills/email-monitor/senders.json`; the Gmail filter is still scoped to the exact address. `✅ Create filter` builds it; `❌ Never` records a permanent decline. Every decision is deduped against state and the live filter list.

**Learning new senders (`sender_ledger.py`):** Every inbound inbox message updates a local tally per exact sender address — how often, over how long, and which policy class (no API or model call; VIPs and the user's own address are never tallied). Once a sender is genuinely recurring (3+ messages spanning 7+ days — so one order's confirmed/shipped/delivered burst doesn't count) and at least two of its subjects agree on one specific label with no tie (hotels and flights are distinct; money labels are never learned), the daemon offers that label — only if it already exists in the user's taxonomy — and offers the ordinary one-tap filing proposal, marked "🆕 New recurring sender". Marketing senders are left to the unsubscribe flow; any security history or unclear subjects produce no proposal at all. Confirming also appends the domain to `learned_senders.json` (merged by `load_config`, curated entries win). A learned domain establishes *who* the sender is, never *what* another address there sends: each new address at that domain still has to earn its own label from its own history. The candidate still passes every existing gate: exact address, live 90-day profile, and the policy-5 evidence rule.

**One-tap bulk cleanup (`confirm:unsub` / `skip:unsub`):** For UNKNOWN recurring bulk senders that have piled up 3+ inbox messages and a consistently-marketing history, the daemon proposes cleanup. A `List-Unsubscribe` header produces `🗑 Unsubscribe & filter`; Gmail's Promotions classification is the fallback when the sender omits that header and produces `🗑 Block sender`. Both create an exact-address Trash filter and clear the inbox backlog after approval. Trash filters never remove Gmail's SPAM label and carry a security-subject exclusion (`email_policy.TRASH_SECURITY_GUARD`), and the backlog clean-up skips security-shaped subjects. Filter and unsubscribe proposal slots are independent, expire after 15 minutes, and recent inbox mail is rechecked so a temporarily occupied slot cannot lose a sender forever.

**Delivery is only "done" with a receipt:** a Telegram notification or calendar proposal that fails to send leaves the email unprocessed so the next poll retries it (a duplicate ping after an ambiguous send is preferred over a lost alert). Each poll step runs independently, so one failing catch-up can never skip the backstop. Security notifications from a sender that fails Gmail's authentication (DMARC) carry a ⚠️ possible-phishing warning — the warning never changes routing.

**Labeled-out backstop:** Archived mail is still watched. Security subjects surface in real time from every label (Travel and dedicated senders included). Material records no catch-up owns go to the 6pm FYI digest (the pre-2026-09-15 realtime set — statements, trades, appointment changes, trip prep — still pings immediately). Mail a dedicated catch-up owns (e.g. a Venmo payment the venmo watcher announces) is never announced twice. Travel-labeled mail is deferred to the travel catch-up only when that catch-up actually handled it as an itinerary; a gate change or check-in reminder it ignored falls back to the backstop. The scan resumes from its last completed pass, so a daemon outage cannot skip archived security alerts.

**Forwarding alarm (`forwarding_watch.py`):** Every 15 minutes the daemon reads Gmail's forwarding addresses and auto-forwarding (read-only) and alerts the user at once if any address appears — even one awaiting confirmation — or auto-forwarding turns on; it reminds daily while it stays on and sends one all-clear when it is off. Undelivered alerts retry; three failed reads in a row alert too. Health is recorded as source `gmail:forwarding`. Never add a forwarding address, delegate or send-as yourself — the `outbound-guard` plugin blocks it.

**Filing model (2026-09-18) — ONE rulebook:** `Skills/email-monitor/refile_spec.json` is the only place filing is decided (`refile_rules.py` reads it). The inbox is for conversations with real people. Automated mail is filed by WHAT it is, one folder per email, first match wins: action items → `Action Needed`; packages; receipts; documents; codes/login/fraud notices → `Records/Notifications/Security` from ANY sender, banks included; then one folder per account (`Finance/Banking|Credit Cards|Crypto|Insurance|Investing|Payments/<account>`, `Finance/Taxes`, `Finance/Credit Monitoring`) or area. No mail sits loose in a parent folder. Junk goes to `Low Priority`, never Trash. **Gmail filters are GENERATED** from the rulebook's `filters` section by `refile_filter_plan.py` (then `apply_filter_migration.py`): each covers one sender's ordinary mail and carries a "doesn't have" clause so receipts, packages, documents and security notices stay in the inbox for arrival filing to file by type. Never hand-write or hand-edit a filter; the generator removes strays (filters the user approved one tap at a time, and junk rules, are kept). `senders.json` destinations follow the same tree. **Arrival filing (`arrival_filing.py`, E1, LIVE)** applies the rulebook each poll to inbox mail the daemon has finished with, asks the fast model one constrained question for unknown senders (a person-looking sender is never filed as junk or a document; the user's own addresses and anyone he corresponds with are never touched), and lets quiet conversations leave (14 days if the user had the last word, 30 if they did); a thread where the user asked and got no reply never leaves on its own. Starred mail is never moved. Mode lives in `arrival_filing.json` (`watch` logs only; only the user changes it); every decision is logged to `logs/arrival_filing.jsonl`. Tools: `refile_plan.py` → `apply_refile.py` (dry run, checksum, undo file), `arrival_report.py` (read-only preview), `cleanup_labels.py` (deletes only empty, childless, unfed folders), `networking_plan.py` (outreach → `Personal/Networking`). A healthy system shows: `refile_plan.py` 0 changes, `refile_filter_plan.py` 0 to remove/create, audit PASS.

**Policy tests and live audit:** Run `python3 Skills/email-monitor/scripts/run_email_policy_tests.py`. It executes the deterministic classification/filter regression suite and then audits live Gmail read-only, profiling each archive/Trash filter's own 90-day mail. Errors: duplicate filters, filters that remove Gmail's SPAM label, protected finance root domains sent to Trash, Trash filters matching security/material mail, missing `@substack.com → Trash`, unknown labels, daemon not running. Gaps (policy violations to migrate): broad-domain archive or Trash rules, security senders auto-filed, mixed-purpose auto-filing, marketing auto-filed or filed under Finance, security/material mail archived with no inbox/backstop/catch-up path, recurring marketing left in Inbox, and a daemon running older code than `email_policy.py`. Use `--skip-live` for code-only tests.

**Broad-rule migration:** `filter_migration_plan.py --live` (read-only) profiles every broad-domain archive rule and writes a JSON plan to `filter_snapshots/`. `apply_filter_migration.py PLAN.json` is a dry run; it only executes with `--execute --expect-sha <sha256 of the approved plan>` after a literal ✅, backs up every filter first, aborts if the live filters drifted from the plan, and verifies the end state.

**Telehealth appointment reminder emails:** Fully automatic — the email daemon detects the provider's appointment reminder emails and sends a Telegram inline button proposal (`confirm:cal` / `skip:cal`). No manual trigger needed. If the user says the booking email is in and no proposal arrived, search Gmail: `from:provider@telehealth.example subject:"Video appointment reminder" newer_than:7d`, extract date/time and video link, then manually build the cal proposal: Title `Appointment <> the user @ <Platform>`, `--location "<Platform>"` (the provider runs its own video platform — NOT Zoom), the join link in description, `--reminder "popup:15m"`, `--start-timezone`/`--end-timezone` for the home zone, the provider's standard length. Confirmation Protocol → `✅` → create → verify by ID. No other emails trashed without an explicit rule.

**Flight confirmations:** Extract airline, flight #, origin, destination, times, confirmation # and create a scoped calendar proposal. Create only after its exact `✅` approval and verify by event ID. Title `AIRLINE_CODE FLIGHT# ORIGIN → DEST <> the user @ FULL_ORIGIN_AIRPORT_NAME` — example: `AA 1234 ORD → DFW <> the user @ O'Hare International Airport`. No brackets, no "Flight to", no category prefix. `--reminder "popup:15m"`, description `ORIGIN HH:MM → DEST HH:MM | Seat: CLASS | Confirmation: CODE`. If Gmail auto-event for the same flight exists, show both and separately propose deletion. Extract fields only — do not store the email body.

**Where the user is staying — check config before asking.** When he is at one of his configured home bases, his lodging is already known: `Skills/email-monitor/travel_config.json` → `homes.<name>`. `drive_time.py` resolves the origin automatically from the active location profile. Do NOT ask "where are you staying" or run `set_trip_lodging.py` for a normal home-base stay — only when he is somewhere with no configured home base.

**In-home services** (massage coach coming to the house, etc.): the event is `... <> the user @ Home` at the home address, 15-min popup only. No leave-by / drive-time / departure reminder — there is no drive.

**Lodging mentioned in conversation, no hotel email** (e.g. "staying at a friend's place downtown"): run `python3 -W ignore Skills/email-monitor/scripts/set_trip_lodging.py --address "<what the user said>"` — no confirmation needed, only adjusts a reminder's timing. Add `--confirmation <code>` only if the user names the trip and more than one is pending; otherwise let the script pick the single pending one (relay its disambiguation error back to the user rather than guessing). Report its output, end with 🎩.

**Checking a bag mentioned in conversation** (e.g. "I'm checking a bag for this one"), for an upcoming flight: run `python3 -W ignore Skills/email-monitor/scripts/set_checked_bag.py` — no confirmation needed, only floors a reminder's leave time at departure-60. Add `--confirmation <code>` only if the user names the trip and more than one is pending; otherwise let the script pick the single pending one (relay its disambiguation error back to the user rather than guessing). Report its output, end with 🎩.

**Hotel confirmations:** Create TWO events — check-in and check-out. Both use `--reminder "popup:15m"`, 30 min blocks. Full address in `--location`. Default times: check-in 3:00 PM, check-out 11:00 AM if not stated. Do not create an all-day block for in-between nights.
- Check-in: `Check-in <> the user @ {Hotel Name}` · description: `Check-out: {Month Day} | Confirmation: {CODE}`
- Check-out: `Check-out <> the user @ {Hotel Name}` · description: `Confirmation: {CODE}`

**Restaurant reservations:** One event, 1.5 hr block. Meal type (Breakfast/Lunch/Dinner) derived from reservation time. `--reminder "popup:15m"`. Full address in `--location`.
- Title: `{Meal Type} <> the user @ {Restaurant Name}` — example: `Dinner <> the user @ Example Bistro`
- Description: `Party of {N} | Confirmation: {CODE}` (omit party or confirmation if not in email)

**Event tickets:** One event. `--reminder "popup:15m"`. Full venue address in `--location`. Default 3 hr duration if no end time stated.
- Title: `{Event/Artist} <> the user @ {Venue Name}` — example: `Artist Name <> the user @ Example Arena`
- Description: `Section {N} · Row {X} · Seat {N} | Order: {CODE}` (omit any fields not present)

**Booking cancellations:** A cancellation email (hotel/flight/restaurant/event) must never produce a "booking detected" proposal — it carries the same property/dates/confirmation as the original, so the itinerary pipeline used to re-propose the trip (`ITINERARY_CANCEL_RE` in `daemon.py` now intercepts these). Instead the daemon looks up any calendar events left behind — by confirmation number, plus a name+stay-window match for the Gmail auto-import and drive-time reminder — and sends a `🗑 Booking cancelled — remove these from your calendar?` proposal on the same `confirm:cal` / `skip:cal` buttons (`action:"delete"`). Confirm removes them (verify-after-delete); skip keeps them.
